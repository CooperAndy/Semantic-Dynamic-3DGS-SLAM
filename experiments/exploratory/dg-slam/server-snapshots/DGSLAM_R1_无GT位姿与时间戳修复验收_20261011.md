## 3. 发现并修复的问题

### 3.1 适配器四元数顺序错误：首个R1运行无效

首次运行`R1_200_20261011_174639`在高斯矩阵转DROID位姿时，误用了`gaussian.common.get_tensor_from_camera(Tquad=True)`。该函数输出`[t,qw,qx,qy,qz]`，而lietorch/DROID要求`[t,qx,qy,qz,qw]`。作者run_tum中同名函数额外重排了四元数，二者不能互换。

该次曾得到7.20 cm ATE，但属于实现错误，**不得当作R1的退化结论**。原始日志、代码、地图、轨迹和初次评价完整保留；运行目录及报告归档均增加`INVALIDATED.json`。

修复采用显式`matrix_to_droid_pose()`，输出`tx ty tz qx qy qz qw`。55个CPU用例覆盖Identity、各轴及任意旋转、随机旋转和平移，与作者正确Tquad=True结果逐项严格相等；lietorch SE3矩阵往返最大误差2.38419×10⁻⁷。实际运行前后也检查所有关键帧转换往返一致，并保存`droid_pose_seeds.npy`。

正确接口重跑`R1_200_20261011_175442`后，ATE为1.8727 cm、33,686个高斯，执行验收通过；但仍保留下一节的作者时间戳缺陷，因此只作历史口径诊断。

### 3.2 作者删除关键帧时未移动时间戳：独立R1.1修复

`FactorGraph.rm_keyframe()`移动images、poses、depth等缓存时，漏掉了`video.tstamp`。CPU审计R0的24个关键帧发现，13个保存的参考位姿与记录帧号对应不上；例如记录帧62的参考位姿实际匹配输入帧82，矩阵匹配误差约10⁻⁷。

R1.1只补入：

```python
self.video.tstamp[ix] = self.video.tstamp[ix+1]
```

CPU回归执行实际rm_keyframe缓存移动代码块，核对12类缓存同步移动；GPU运行对每次GS派发额外计算缓存RGB哈希，与预加载200帧的真实RGB哈希对应，要求实际帧号等于video.tstamp。24次全部通过。

R0及未修时间戳的R1原始配置、轨迹、指标和原验收回执不改写，另加`POST_AUDIT_TIMESTAMP_NOTE.json`限定适用范围。此前“时间戳匹配输入索引”只检查最终导出时间戳，未覆盖内部关键帧RGB身份；后续必须保留此次更严格的检查。

**R0的2.044 cm、旧R1的1.873 cm和R1.1的1.750 cm不构成高斯收益的独立消融。**它们含GT协议、时间戳修复及单次GPU运行差异；不以百分比改善作为采用新方法的证据。

## 5. 下一步：高斯位姿精修开／关对照

建议下一项为`T3-DG-T01`：以R1.1为共同入口，保持同一RGB-D、mask、时间戳修复、初始化、mapping规则与种子，比较“DROID初值直接入图”和“DROID初值经过高斯位姿精修后入图”。这才能回答当前研究问题：高斯可微渲染提供的位姿修正是否有效。

| ID | 建议责任 | 必须交付 / 验收 |
|---|---|---|
| T3-DG-T01-P | B主、A核查 | 预登记精修开关与预算；保存每个实际帧号的粗位姿、精修位姿、损失与耗时；不再修改时间戳或GT协议 |
| T3-DG-T01-D | A/B | 同一窗口配对运行；关键帧精修前后与最终补全轨迹分开评价；保留全部帧失败/缺失率和资源成本 |
| T3-DG-T01-Q | A/B | 单窗口仅作DEV诊断；正式采用仍需至少2个预登记窗口、每组3固定种子：ATE平均下降≥10%、平移RPE下降≥5%，任一窗口退化≤5%，失败率不增加 |

关闭精修会减少实际优化工作量，须如实报告耗时，不能声称两组消耗了完全相同算力。首次只改变tracking精修开关；mapping点插入、损失、剪枝等维持一致。建图质量后续按固定位姿与留出视角单独消融；不能用本轮点数或ATE替代mapping质量证据。
